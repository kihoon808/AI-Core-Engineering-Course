# basic 실습 요약 및 학습 정리 노트

LLM을 서비스에 안전하고 안정적으로 도입하기 위한 8단계 엔지니어링 핵심 패턴 정리입니다.

---

## 1. 실습별 핵심 요약

| 실습 | 주제 | 핵심 내용 (쉬운 설명) |
|---|---|---|
| **01** | 첫 호출 (`01_first_call`) | API 기본 연결과 호출 메타데이터 수집 (응답 시간, 상태 확인) |
| **02** | 구조화된 출력 (`02_structured_output`) | 자유 형식 텍스트 대신 정해진 JSON 스키마로 출력 강제 (답변 여부, 출처 ID, 누락 정보) |
| **03** | 스트리밍 (`03_streaming`) | 전체 응답을 기다리지 않고 첫 글자(TTFT)를 빠르게 표시, 수신 종료 후 전체 스키마 검증 |
| **04** | 오류와 재시도 (`04_errors_retry`) | 재시도할 오류(429, 503)와 멈춰야 할 오류(401, 400)를 구분하고 지수 백오프 적용 |
| **05** | 사용량과 비용 (`05_usage_cost`) | 입력 토큰에서 캐시 토큰을 분리해 각각 단가 적용, 정밀한 Decimal 비용 계산 |
| **06** | 승인 응답 캐시 (`06_response_cache`) | 모델-질문-컨텍스트 전체로 캐시 키 생성, 사람이 직접 검토/승인한 답변만 재사용 |
| **07** | 모델 선택 (`07_model_routing`) | 임의 자동 대체(fallback) 없이 빠름(fast)과 품질(quality)을 명시적으로 선택해 비교 |
| **08** | 종합 프로젝트 (`08_daily_project`) | 스트리밍 호출, 정형 출력, 캐싱, 비용 추적을 연결한 파이프라인 완성 |

---

## 2. 기억해야 할 5가지 핵심 원칙

1. **자동 검증과 사람 평가는 분리한다**
   - JSON 스키마 통과(`status: validated`)는 형식이 올바르다는 뜻일 뿐, 답변 내용이 사실인지는 사람이 직접 근거를 대조해 검토(`review.py`)해야 합니다.

2. **비용 계산 시 캐시와 추론 토큰에 주의한다**
   - 캐시 토큰(`cached_tokens`)은 입력 토큰에 이미 포함되어 있으므로 `입력 - 캐시`로 분리해 서로 다른 단가를 매겨야 합니다.
   - 추론 토큰(`reasoning_tokens`)은 출력 토큰에 이미 포함되어 있으므로 이중으로 더하지 않습니다.

3. **캐시 키는 컨텍스트 본문 전체를 반영해야 한다**
   - 질문이나 문서 ID만으로 캐시 키를 만들면 본문이 바뀌었을 때 과거 엉뚱한 답변이 재사용됩니다.
   - 전체 프롬프트와 컨텍스트 본문 해시를 결합해야 내용 변경 시 정상적으로 캐시 미스가 발생합니다.

4. **실패와 누락을 0으로 덮지 않는다**
   - 오류로 인해 사용량 측정이 안 된 응답을 `0`으로 채우면 전체 운영 비용이 실제보다 왜곡되어 축소 집계됩니다. 모르는 값은 `None`으로 남겨 결측치를 추적합니다.

5. **임의 자동 fallback은 숨은 비용과 장애를 유발한다**
   - 권한이나 예산이 없다고 시스템이 알아서 다른 모델로 돌려버리면 품질 저하나 예산 초과가 발생합니다. 라우팅은 명시적으로 설계하고, 권한이 없으면 명확한 오류로 처리합니다.
